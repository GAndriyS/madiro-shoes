# Deployment (Railway)

Madiro runs as **three services plus a managed Postgres, twice** — once per
environment — inside the Railway project `splendid-youthfulness`:

| Environment  | Deploys from | Purpose                                                        |
| ------------ | ------------ | -------------------------------------------------------------- |
| `demo`       | `main`       | every merge lands here; data is disposable and may be reseeded |
| `production` | `release`    | the shop's real books; only tagged releases arrive             |

Domains, all under `.up.railway.app`:

| Service     | `demo`                        | `production`                |
| ----------- | ----------------------------- | --------------------------- |
| `api`       | `madiro-shoes-production`     | `api-production-bfcf`       |
| `scanner`   | `keen-warmth-production-8537` | `scanner-production-b680`   |
| `dashboard` | `dashboard-production-2dab`   | `dashboard-production-fb99` |

The demo names read oddly because that environment was the original one and
kept its generated domains when it was renamed — the installed PWAs and the
bookmarks point at them, and regenerating would have broken both. Read the
`-production` suffix as "generated by Railway", not as "this is PROD".

Both run the same image and the same `NODE_ENV=production`. What separates them
is `APP_ENV` (`demo` / `production`), which decides what is _allowed_: the
demo seed is refused in production, as are `VISION_PROVIDER=mock` and a pinned
`EXCHANGE_RATE_USD`. Each environment has its **own Postgres, own domains and
own secrets** — nothing is shared, and no code knows which environment it is in
until the API tells it.

Services in each environment:

| Service     | Source                      | Notes                                    |
| ----------- | --------------------------- | ---------------------------------------- |
| `api`       | `apps/api/Dockerfile`       | migrates + seeds the admin on every boot |
| `scanner`   | `apps/scanner/Dockerfile`   | PWA; Caddy proxies `/api`                |
| `dashboard` | `apps/dashboard/Dockerfile` | Caddy proxies `/api` and `/socket.io`    |
| Postgres    | Railway plugin              | one per environment, never shared        |

Each frontend container serves its static bundle **and reverse-proxies `/api` to
the api service over Railway's private network** (see `apps/scanner/Caddyfile`).
The browser therefore talks to a single origin per app. That is not cosmetic:
`up.railway.app` is on the public suffix list, so separate subdomains are
separate _sites_, the httpOnly refresh cookie was third-party, WebKit dropped
it, and the installed PWA asked for a login on every launch.

Because the frontends take **no build arguments**, a bundle is environment-
agnostic: the same artefact works in either environment, and everything that
differs is a runtime variable.

## One-time setup

### 1. Project and databases

Each environment owns a Postgres plugin. Duplicating an environment creates a
**new, empty** volume — data is never copied.

### 2. Services

For **each** of `api`, `scanner`, `dashboard`:

- **Root Directory:** repo root (leave default `/`) — the Docker build needs the
  whole pnpm workspace.
- Variable **`RAILWAY_DOCKERFILE_PATH`** = the service's Dockerfile
  (`apps/api/Dockerfile`, `apps/scanner/Dockerfile`, `apps/dashboard/Dockerfile`).
- **Branch:** `main` in `demo`, `release` in `production`. This is what makes
  deployment automatic and is the only source-level difference between the two.
- Generate a public domain (Settings → Networking → Generate Domain).
- **Watch Paths** so a push only rebuilds what changed:
  - api: `apps/api/**`, `packages/**`, `package.json`, `pnpm-lock.yaml`
  - scanner: `apps/scanner/**`, `packages/**`, `package.json`, `pnpm-lock.yaml`
  - dashboard: `apps/dashboard/**`, `packages/**`, `package.json`, `pnpm-lock.yaml`

  > `package.json` matters: a release whose only change is the version bump
  > touches nothing else, and without it the release would deploy nothing.

- Enable **wait for CI** so a deploy starts only after the GitHub checks on that
  branch pass.

### 3. Environment variables

**api**:

| Variable             | `demo`                                 | `production`                           |
| -------------------- | -------------------------------------- | -------------------------------------- |
| `APP_ENV`            | `demo`                                 | `production`                           |
| `NODE_ENV`           | `production`                           | `production`                           |
| `DATABASE_URL`       | `${{Postgres.DATABASE_URL}}`           | `${{Postgres.DATABASE_URL}}`           |
| `JWT_ACCESS_SECRET`  | 32+ chars, `openssl rand -hex 32`      | **a different value**                  |
| `JWT_REFRESH_SECRET` | a different 32+ char value             | **a different value**                  |
| `CORS_ORIGINS`       | that environment's scanner + dashboard | that environment's scanner + dashboard |
| `OPENROUTER_API_KEY` | recognition backend                    | recognition backend                    |
| `ADMIN_PASSWORD`     | seeds the admin on a fresh database    | **a different password**               |
| `PORT`               | `3000`                                 | `3000`                                 |

Reference variables (`${{Postgres.DATABASE_URL}}`) resolve **within the
environment**, so the same expression points at each environment's own database.

`ADMIN_LOGIN` (default `admin`), `ADMIN_NAME`, `LOG_LEVEL` (defaults to `info`)
and `OPENROUTER_MODEL` are optional. `GEMINI_API_KEY` is an alternative vision
backend, unused while an OpenRouter key is set.

> Set `PORT` **explicitly to `3000`**. Railway injects a `PORT` of its own, but
> the frontends reference `${{api.PORT}}` to build their upstream URL, and an
> auto-injected value is not reliably referenceable from another service.

> Secrets must **not** be shared between environments. A leaked demo token must
> never open the real books.

**scanner** and **dashboard** — one runtime variable each:

| Variable       | Value                                                  |
| -------------- | ------------------------------------------------------ |
| `API_UPSTREAM` | `http://${{api.RAILWAY_PRIVATE_DOMAIN}}:${{api.PORT}}` |

Read at **runtime** by Caddy, so changing it needs a restart, not a rebuild. It
stays on the private network — plain `http`, no public egress. There is no
`VITE_API_URL`: the bundle calls a relative `/api`.

### 4. First deploy order

Deploy **api** first (it runs `prisma migrate deploy` and seeds the admin on
boot — see `apps/api/docker-entrypoint.sh`), then the two frontends. Set
`API_UPSTREAM` on the frontends and `CORS_ORIGINS` on the api once the domains
are known.

## Which build is running?

```bash
curl -s https://api-production-bfcf.up.railway.app/api/health
# {"status":"ok","database":"up","version":"1.2.0","env":"production","commit":"a1b2c3d"}
```

`version` is the released version from the workspace root `package.json`; `env`
is `APP_ENV`; `commit` is what Railway built. The same payload drives the badge
under each login screen — version always, plus a **DEMO** tag when `env` is
`demo`, so nobody mistakes one environment for the other.

## Continuous deployment

- **DEMO** — merging a PR into `main` deploys it. CI gates the PR first.
- **PROD** — `pnpm release` fast-forwards `release` and Railway deploys that.
  See [docs/release-process.md](docs/release-process.md), which also covers
  rollback and the backward-compatibility rule migrations must follow.

Railway builds the same Dockerfiles you can build locally:

```sh
docker build -f apps/api/Dockerfile -t madiro-api .
docker build -f apps/scanner/Dockerfile -t madiro-scanner .
docker build -f apps/dashboard/Dockerfile -t madiro-dashboard .
docker run -p 8080:8080 -e API_UPSTREAM=http://host.docker.internal:3000 madiro-scanner
```

## Resetting DEMO data

DEMO is meant to be disposable. The demo seed **wipes operations, pairs and
variants** (accounts survive) and writes a deterministic dataset:

```sh
railway ssh --service api --environment demo
pnpm --filter @madiro/api db:seed:demo
```

The same command in `production` refuses to run — the guard is `APP_ENV`, not a
convention.

## Admin & seller accounts

- The **admin** is seeded on the api's first boot from `ADMIN_LOGIN` /
  `ADMIN_PASSWORD`. The seed is idempotent: once the admin exists it never
  rewrites the password, so `ADMIN_PASSWORD` only matters on a fresh database.
  To change it later, open a shell on the running api:

  ```sh
  railway ssh --service api --environment production
  pnpm --filter @madiro/api admin:reset-password
  ```

  It bumps `tokenVersion`, so every existing admin session is revoked at once.

  > This is also the fix when an environment was created by duplication: the
  > admin may already exist with the password copied from the source
  > environment, and changing the variable alone will not replace it. That is
  > not a hypothetical — it is what happened when `production` was created, and
  > the real books were briefly reachable with the demo password.

  The same shell is available without the CLI: Railway dashboard → the `api`
  service → **Console**. Run workspace scripts through `pnpm --filter`, not by
  calling `node` from `/app`: this is a pnpm workspace, so `@prisma/client`
  resolves under `apps/api/node_modules`, and a bare `node -e` from the repo
  root cannot find it.

- **Sellers** are created from the dashboard (admin → users), not by seeding.

## Verifying from a phone

The scanner needs a **secure context** for the camera (`getUserMedia`) and the
service worker — Railway domains are HTTPS, so this works out of the box:

1. Open the scanner domain, log in (`admin` / your `ADMIN_PASSWORD`, or a seller
   created in the dashboard).
2. Add to Home Screen to install the PWA.
3. Intake → the camera opens (grant permission); scan a box label.

A PWA installed from the demo domain stays pointed at demo; installing the
production one is a separate install.
