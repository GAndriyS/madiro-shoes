# Madiro — план ручного E2E-тестування

> Повний прохід функціоналу обома застосунками (сканер + дашборд) проти
> реального бекенду. План розрахований на двох виконавців: **людину**
> (тестувальник із телефоном і ноутбуком) та **АІ-агента** (браузерна
> автоматизація + перевірки через API). Джерело правди щодо поведінки —
> [spec.md](spec.md).

---

## 0. Конвенції (обов'язково прочитати перед проходом)

### 0.1 Формат кейса

Кожен тест-кейс має стабільний ідентифікатор `TC-<суїта>-<номер>` і поля:

- **Роль / застосунок** — під ким і де виконувати.
- **Передумови** — стан, що має існувати. Якщо вказано `після TC-X-NN` —
  кейс залежить від результату іншого кейса; виконуйте в порядку розділу
  «Маршрут проходження» наприкінці документа.
- **Кроки** — нумеровані дії. Один крок = одна дія користувача.
- **Очікується** — перелік тверджень, що перевіряються. Кожне твердження
  або істинне (кейс пройдено), або ні (кейс провалено; занотуйте крок).
- **Змінює стан** — що лишається в БД після кейса (для ланцюжків).

### 0.2 Правила для АІ-агента

- Елементи UI шукати передусім за **`data-testid`** (стабільні, не залежать
  від мови та копірайту; конвенція — `<область>-<елемент>`, а для груп
  варіантів `<група>-<ENUM>`: `payment-CARD`, `season-BAIKA`). Видимий текст —
  для перевірки самого напису; точні написи наведено в лапках «…» і взяті з
  i18n-словників.
- **В'юпорти:** сканер — мобільний (375×812), дашборд — десктоп
  (1280×800). Людина-тестувальник для сканера користується телефоном
  або звуженим вікном.
- Суми відображаються у форматі `2 850 ₴` (нерозривні пробіли між
  розрядами). Порівнюйте числове значення, а не рядок посимвольно.
- Час/дати залежать від моменту прогону: твердження на кшталт
  «сьогодні», «вчора» перевіряти відносно годинника **Europe/Kyiv**.
- **API-перевірки:** базовий URL `http://localhost:3000/api`. Токен:

  ```bash
  curl -s -X POST http://localhost:3000/api/auth/login \
    -H 'Content-Type: application/json' \
    -H 'x-madiro-client: scanner' \
    -d '{"login":"iryna","password":"iryna-2026"}'   # → accessToken у тілі
  ```

  Заголовок `x-madiro-client` (`scanner` | `dashboard`) обов'язковий на всіх
  `/auth/*`: він і захист від CSRF, і вибір того, чию refresh-куку видати.
  Без нього — 403.

  Далі — заголовок `Authorization: Bearer <accessToken>`. Креденшали
  адміна — `ADMIN_LOGIN` / `ADMIN_PASSWORD` з `.env`.
- **SQL-доступ** (лише де кейс явно вимагає):
  `docker compose exec postgres psql -U madiro -d madiro`.
- **Статуси кейсів:** `PASS` (усі твердження істинні) · `FAIL` (хоч одне
  хибне; занотувати крок, очікуване/фактичне, скріншот) · `SKIPPED`
  (кейс позначено «опційно» і середовище не дозволяє) · `BLOCKED`
  (не виконати через провал попереднього кейса-передумови).
- Кейси, позначені «опційно», пропускати можна; всі інші — обов'язкові.
- Кейси, позначені **«лише людина»**, агент пропускає зі статусом SKIPPED:
  вони потребують реального пристрою або живої моделі (суїти M і N).
- Кейси з міткою **«покрито Playwright»** можна не проходити руками —
  вони перевіряються автоматично (`pnpm e2e:pw`), а ручний прохід лишається
  як опція для візуальної перевірки.
- Скріншоти робити на кожен провалений крок.

**Практика браузерної автоматизації** (перевірено прогоном 30.07.2026 —
[test-run-2026-07-30.md](test-run-2026-07-30.md)):

- Поля вводу заповнювати **нативним сеттером** з подією `input`, інакше React
  не побачить значення:
  ```js
  const set = Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set;
  set.call(el, '38'); el.dispatchEvent(new Event('input', { bubbles: true }));
  ```
- Кліки робити через `element.click()`, а не по координатах.
- **Дві дії, що змінюють стан, — у двох окремих викликах** з паузою: React
  батчить оновлення, і другий обробник побачить старий стан (наприклад,
  «Картка» + «Підтвердити продаж» в одному блоці збережуть оплату CASH).
- Після кожної дії — пауза 1–2 с і повторне читання сторінки; знімок
  сторінки буває закешованим.

### 0.3 Середовище

Одна команда приводить середовище до відомого стану — збірка (включно з
`@madiro/shared`), Postgres, міграції, сіди й перевірка, що на порту 3000 не
висить застарілий процес:

```bash
pnpm test:reset
```

Далі — три сервіси (кожен у своєму терміналі):

```bash
pnpm --filter @madiro/api dev            # API http://localhost:3000/api
pnpm --filter @madiro/dashboard dev      # http://localhost:5173
pnpm --filter @madiro/scanner dev        # http://localhost:5174
```

> **Якщо запускаєте руками, а не через `pnpm test:reset`:** збірка
> `@madiro/shared` обов'язкова (застарілий `dist` раніше давав чорний екран;
> тепер сторінка покаже «Застосунок не запустився» з причиною), і на порту
> 3000 має працювати щойно запущений API — старий процес приймає логін, але
> завжди віддає 403 на `/auth/refresh`, і сесія не переживає перезавантаження.

> **Дві сесії в одному браузері — це нормально.** Кожен застосунок має власну
> refresh-куку (`madiro_refresh_scanner` / `madiro_refresh_dashboard`), тож
> продавець у сканері й адмін у дашборді співіснують в одному профілі:
> перезавантаження сторінки більше не перетворює одного на іншого. Кейси «два
> вікна» (TC-H-04, TC-J-04) виконуються у звичайних вкладках.

- **Мок-розпізнавання**: будь-яке фото читається як `SIZE 38 · COLOR 36 ·
  STYLE 7645` (confidence 0.99). Вмикається автоматично без `GEMINI_API_KEY`,
  а з ключем — прапорцем `VISION_PROVIDER=mock` у `.env` (у production
  заборонено). Ставте його на час прогону: інакше кейси розпізнавання
  залежать від того, що жива модель прочитає з фото, і витрачають квоту.
  Кейси реального розпізнавання — окрема суїта N.
- Акаунти: адмін — логін/пароль із `.env` (`ADMIN_LOGIN`/`ADMIN_PASSWORD`),
  продавці — `olia` / `olia-2026` та `iryna` / `iryna-2026`.
- Скидання стану: повторний `db:seed:demo` (операції/пари/варіанти
  перезаливаються, користувачі лишаються).

## Суїта A — смоук і автентифікація

### TC-A-01 · Смоук: усе піднялося
- **Роль:** без логіна.
- **Кроки:**
  1. Відкрити `http://localhost:3000/api/health`.
  2. Відкрити `http://localhost:5173` (дашборд).
  3. Відкрити `http://localhost:5174` (сканер).
- **Очікується:**
  - Health повертає 200 і `"status":"ok"`.
  - Обидва фронтенди показують екран входу з полями «ЛОГІН» і «ПАРОЛЬ».
- **Змінює стан:** ні.

### TC-A-02 · Вхід продавця у сканер
- **Роль:** продавець · сканер.
- **Кроки:**
  1. Ввести `olia` / `olia-2026`, натиснути «Увійти».
- **Очікується:**
  - Головна-хаб: привітання «Добрий день, Оля», картки дій «Продаж /
    вихід», «Поступлення», «Повернення від покупця», «Ввести вручну»,
    «Пошук по складу», картка «МОЇ ПРОДАЖІ СЬОГОДНІ».
- **Змінює стан:** ні (оновлюється лише lastActiveAt).

### TC-A-03 · Невірний пароль
- **Роль:** без логіна · сканер.
- **Кроки:**
  1. Ввести `olia` / `wrong-password`, натиснути «Увійти».
- **Очікується:**
  - Повідомлення «Невірний логін або пароль»; вхід не відбувся.
- **Змінює стан:** ні.

### TC-A-04 · Вхід адміна в дашборд
- **Роль:** адмін · дашборд.
- **Кроки:**
  1. Увійти з креденшалами адміна з `.env`.
- **Очікується:**
  - Відкривається «Огляд»; у навігації — Огляд · Склад · Поступлення ·
    Користувачі; бейдж черги біля «Поступлення» показує кількість
    варіантів у черзі (після сіда — 1).
- **Змінює стан:** ні.

### TC-A-05 · Продавець не входить у дашборд
- **Роль:** продавець · дашборд.
- **Кроки:**
  1. На `5173` увійти як `iryna` / `iryna-2026`.
- **Очікується:**
  - Повідомлення «Дашборд доступний лише адміністратору»; всередину не
    пускає.
- **Змінює стан:** ні.

### TC-A-06 · Сесія переживає перезавантаження
- **Роль:** адмін · дашборд (залогінений).
- **Кроки:**
  1. Перезавантажити сторінку (F5).
- **Очікується:**
  - Після короткого завантаження користувач лишається всередині (silent
    refresh по httpOnly-куці), редіректу на логін немає.
- **Змінює стан:** ні.

### TC-A-07 · Вихід
- **Роль:** адмін · дашборд.
- **Кроки:**
  1. Натиснути «Вийти».
  2. Натиснути «назад» у браузері.
  3. Перезавантажити сторінку.
- **Очікується:**
  - Після виходу — екран логіна; «назад»/перезавантаження не повертає в
    застосунок (кука знята, сесія не відновлюється).
- **Змінює стан:** ні.

### TC-A-08 · Перемикач мови на вході
- **Роль:** без логіна · сканер.
- **Кроки:**
  1. На екрані входу перемкнути мову на EN.
  2. Повернути УКР.
- **Очікується:**
  - Написи перекладаються (EN: "LOGIN", "PASSWORD"); вибір зберігається
    після перезавантаження.
- **Змінює стан:** ні (лише localStorage мови).

## Суїта B — сканер: поступлення

### TC-B-01 · Продавець створює чернетку вручну
- **Роль:** продавець (`olia`) · сканер.
- **Кроки:**
  1. З головної — «Поступлення».
  2. На екрані камери — «Ввести вручну».
  3. Заповнити SIZE `38`, COLOR `07`, STYLE `4001`; утеплення й матеріал
     не чіпати.
  4. Натиснути «Зберегти й завершити».
- **Очікується:**
  - Форма «Нове поступлення» з бейджем «ПРОДАВЕЦЬ»; секції ціни немає;
    є пояснення про чергу «Очікують ціни».
  - Після збереження — повернення на головну. (Тоста тут немає: «Зберегти
    й завершити» одразу навігує, тост показується лише в пакетному режимі.)
- **Змінює стан:** так — чернетка `4001·07 р.38` (Оля).

### TC-B-02 · Пакетний режим продавця
- **Роль:** продавець (`olia`) · сканер.
- **Кроки:**
  1. «Поступлення» → «Ввести вручну» → SIZE `39`, COLOR `07`, STYLE `4001`.
  2. Натиснути «У чернетки і сканувати наступну».
- **Очікується:**
  - Тост «Чернетку збережено»; користувач повертається на **екран камери**
    поступлення (пакетний режим завжди веде до сканування наступної
    пари; для ручного вводу — знову «Ввести вручну»), а не на головну.
- **Змінює стан:** так — чернетка `4001·07 р.39` (Оля).

### TC-B-03 · Адмін приймає пару з ціною
- **Роль:** адмін · сканер.
- **Кроки:**
  1. Увійти в сканер як адмін.
  2. «Поступлення» → «Ввести вручну» → SIZE `40`, COLOR `12`, STYLE `5555`,
     утеплення «Байка», матеріал «Шкіра».
  3. У полі «ЦІНА ЗАКУПКИ» ввести `1650`.
  4. «Зберегти й завершити».
- **Очікується:**
  - Форма з бейджем «АДМІН» і секцією «ЦІНА ЗАКУПКИ».
  - Тост «Пару додано на склад»; пара не потрапляє в чергу «Очікують ціни».
- **Змінює стан:** так — новий варіант `5555·12 Шкіра·Байка`, закупка
  1 650 ₴, пара р. 40 на складі.

### TC-B-04 · Підказка ціни для відомого варіанта
- **Роль:** адмін · сканер.
- **Кроки:**
  1. «Поступлення» → «Ввести вручну».
  2. Заповнити SIZE `38`, COLOR `36`, STYLE `7645`, утеплення «Овчина»,
     матеріал «Шкіра» (= сідовий варіант).
- **Очікується:**
  - У полі ціни автоматично з'являється `1400` і підпис «Підставлено ціну
    цього варіанта — змініть, якщо потрібно».
- **Змінює стан:** ні (не зберігати; натиснути «Назад»).

### TC-B-05 · Підказка ціни зникає при зміні варіанта (регресія S-4)
- **Роль:** адмін · сканер.
- **Кроки:**
  1. Повторити кроки TC-B-04 (у полі — 1400).
  2. Змінити STYLE на `9999` (невідомий системі).
- **Очікується:**
  - Поле ціни **очищається**, підпис підказки зникає — ціна чужого
    варіанта не успадковується.
- **Змінює стан:** ні (вийти без збереження).

### TC-B-06 · «Без ціни — старий товар» при поступленні
- **Роль:** адмін · сканер.
- **Кроки:**
  1. «Поступлення» → «Ввести вручну» → SIZE `41`, COLOR `02`, STYLE `6001`.
  2. Увімкнути тумблер «Без ціни — старий товар».
  3. «Зберегти й завершити».
- **Очікується:**
  - Поле ціни ховається, замість нього — «Вказати ціну · без ціни»;
    збереження проходить.
  - Пара на складі; в чергу «Очікують ціни» не потрапляє.
  - У БД `variants.purchasePrice = 0` (а не NULL), у складі — «Без ціни».
- **ВІДОМИЙ ДЕФЕКТ (BUG-2):** сканер зберігає `NULL` замість `0`, тож склад
  показує «вказати». Дашбордний шлях «Без ціни» (TC-C-03) пише `0` коректно.
  Див. [test-run-2026-07-30.md](test-run-2026-07-30.md) §2.
- **Змінює стан:** так — варіант `6001·02`, закупка «Без ціни», пара р. 41.

### TC-B-07 · Скан-флоу з мок-розпізнаванням — покрито Playwright
- **Роль:** адмін або продавець · сканер (dev без GEMINI-ключа).
- **Кроки:**
  1. «Поступлення» → зробити фото (будь-яке) або «Обрати фото з галереї».
- **Очікується:**
  - Стан «Розпізнаємо бірку…», далі форма з префілом SIZE `38`,
    COLOR `36`, STYLE `7645`; жовтої підказки про невпевненість немає
    (confidence 0.99).
- **Змінює стан:** ні (вийти без збереження).

### TC-B-08 · «Ввести вручну» з екрана помилки лишає у флоу — покрито Playwright
- **Роль:** продавець · сканер.
- **Кроки:**
  1. У DevTools → Network заблокувати запити до `/api/tags/recognize`
     (Request blocking) і сфотографувати бірку в «Поступленні».
  2. На екрані «Не вдалося прочитати бірку» натиснути «Ввести вручну».
  3. Зняти блокування запитів.
- **Очікується:**
  - Відкривається форма поступлення з порожніми полями — **не** екран
    продажу.
- **Змінює стан:** ні.

### TC-B-09 · Валідація порожніх полів
- **Роль:** будь-хто · сканер.
- **Кроки:**
  1. «Поступлення» → «Ввести вручну» — поля порожні.
- **Очікується:**
  - Кнопки збереження неактивні, доки SIZE/COLOR/STYLE не заповнені.
- **Змінює стан:** ні.

### TC-B-10 · Підказка для варіанта «без ціни» вмикає той самий режим
- **Роль:** адмін · сканер.
- **Передумови:** після TC-B-06 (існує `6001·02` із закупкою 0).
- **Кроки:**
  1. «Поступлення» → «Ввести вручну» → SIZE `42`, COLOR `02`, STYLE
     `6001` (утеплення/матеріал — як у TC-B-06, тобто не чіпати).
- **Очікується:**

## Суїта H — дашборд: огляд і realtime

### TC-H-01 · KPI за сьогодні
- **Роль:** адмін · дашборд.
- **Передумови:** після суїт D, E, C. Потрібен хоча б один чинний
  (неповернений) продаж за сьогодні: якщо TC-D-07 пропущено — продати
  `9031·14 р.37` за `2400` «Готівка» через «Ввести вручну» перед цим
  кейсом.
- **Кроки:**
  1. «Огляд», період «Сьогодні».
- **Очікується:**
  - «ВИРУЧКА» = сума сьогоднішніх продажів мінус повернення. Якщо
    маршрут виконано точно (D-07 SKIPPED, фолбек-продаж зроблено):
    продажі 2 200 + 3 100 + 1 500 + 1 300 + 1 350 + 2 400, повернення
    2 200 + 3 100 + 1 500 + 1 350 → **виручка 3 700 ₴**; поруч дельта
    «% до вчора» (вчора — 2 850 ₴, тобто +30%).
  - «ПРОДАНО»: 6 продажів · 4 повернення · нетто 2 пари.
  - «МАРЖА» рахується лише по операціях із закупкою: 9031 (2 400 −
    2 100) + 7100·Без (1 300 − 1 000) = **600 ₴** (повернені продажі не
    входять; продаж `5211` повернено, тож його бекфілнута маржа теж ні).
  - *Значення підтверджені прогоном 30.07.2026 — збіглися точно.*
  - Темна картка «ОЧІК. ЦІНИ» = 0 (черга спорожнена в суїті C); клік
    веде в «Поступлення».
- **Змінює стан:** ні.

### TC-H-02 · Періоди і довільний діапазон
- **Роль:** адмін · дашборд.
- **Кроки:**
  1. Перемкнути «Тиждень», «Місяць».
  2. «Період» → обрати діапазон, що включає вчора й сьогодні.
- **Очікується:**
  - KPI перераховуються; сідовий продаж 2 850 ₴ (вчора) входить у
    тиждень/місяць/діапазон, але не в «Сьогодні».
  - Графік: погодинний для «Сьогодні», поденний для решти.
- **Змінює стан:** ні.

### TC-H-03 · Стрічка останніх операцій
- **Роль:** адмін · дашборд.
- **Кроки:**
  1. Переглянути «Останні операції».
- **Очікується:**
  - Всі операції прогону (продажі, повернення, списання, поступлення) з
    часом, парою, типом, продавцем, оплатою, сумою; маржа — де є basis.
- **Змінює стан:** ні.

### TC-H-04 · Realtime: дашборд оновлюється без перезавантаження
- **Роль:** адмін · дашборд + продавець · сканер (друге вікно).
- **Кроки:**
  1. Тримати «Огляд» відкритим; НЕ перезавантажувати.
  2. У сканері продавцем створити чернетку (STYLE `4003`).
  3. Спостерігати за дашбордом ≤5 секунд.
- **Очікується:**
  - Бейдж черги, віджет «Очікують ціни» і стрічка операцій оновлюються
    самі (Socket.io), без F5.
- **Змінює стан:** так — чернетка `4003·07` (не видаляти — потрібна для
  TC-G-02 і TC-K-04).

## Суїта K — безпека (API-рівень; для агента обов'язково)

> **Покрито Playwright** — `e2e/tests/security.spec.ts` виконує TC-K-01…04
> автоматично (`pnpm e2e:pw`), включно з рекурсивним скануванням відповідей
> на цінові поля. Ручний прохід нижче лишається для позапланових перевірок.
>
> Виконується HTTP-запитами. Токени: `POST /api/auth/login`
> `{login, password}` → `accessToken` у тілі.

### TC-K-01 · 401 без токена
- **Кроки:** `GET /api/me/summary` без заголовка Authorization.
- **Очікується:** 401.

### TC-K-02 · 403 продавцю на адмін-ендпоінтах
- **Кроки:** з токеном продавця викликати:
  `GET /api/stock/variants`, `GET /api/intake/queue`,
  `GET /api/intake/history`, `GET /api/intake/price-hint`,
  `GET /api/stats/overview?period=today`, `GET /api/users`.
- **Очікується:** 403 на кожен.

### TC-K-03 · Відповіді продавцю не містять цін закупки (FR-B-02)
- **Кроки:** з токеном продавця:
  1. `POST /api/sale/lookup` для відомої пари.
  2. `GET /api/sale/search?style=7645`.
  3. `GET /api/me/drafts`, `GET /api/me/sales?period=today`.
- **Очікується:** у жодній відповіді немає полів
  `purchasePrice` / `margin` / `purchasePriceAtTime` (перевірити повний
  JSON рекурсивно).

### TC-K-04 · Чужі чернетки та адмін-дії недоступні продавцю
- **Кроки:** з токеном продавця `iryna`:
  1. `GET /api/me/drafts` токеном `olia` → взяти `pairId` її чернетки
     (за маршрутом у Олі лишається чернетка `4003·07` з TC-H-04).
  2. `PATCH /api/intake/<pairId>` токеном `iryna` (будь-яке валідне тіло).
  3. `DELETE /api/intake/<pairId>` токеном `iryna`.
  4. `POST /api/stock/operations/<будь-який id>/cancel` токеном `iryna`.
- **Очікується:** кроки 2–3 → 404 (чужа чернетка «не існує» для іншого
  продавця); крок 4 → 403.

### TC-K-05 · Rate limit логіна
- **Кроки:** ≥10 швидких `POST /api/auth/login` з невірним паролем.
- **Очікується:** з'являється 429 (throttling); нормальний вхід
  відновлюється після паузи.
- **Увага:** виконувати в самому кінці прогону — тимчасово блокує вхід.
